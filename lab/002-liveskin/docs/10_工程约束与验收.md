# 07 · 工程约束与验收

> 本文是本目录下的**强制规范**。任何朋克皮肤家族在合并前都必须逐条满足。
> 这些不是风格建议，而是从 LiveSkin 已经踩过的真实故障与已建成的检查中反推出来的底线。

---

## 一、为什么需要这份文档

皮肤是纯 CSS + 资产，跑在别人写好的界面之上。它最容易出的不是「不好看」，而是三类**静默失效**：

1. **写了不生效**——声明在了错误的层级，被官方样式盖住，界面看起来只是「没变」。
2. **看不见的坏对比**——深色皮肤里某个状态色与背景挤在一起，只在特定状态（hover / disabled / 选中）才暴露。
3. **拖垮主线程**——大面积实时模糊、全屏逐帧重绘，用户以为是产品卡了。

这三类都不会报错，只会让人觉得「这皮肤有问题」。所以每一条约束都配一条可自动化的检查。

---

## 二、硬约束

### C1 · `--dsw-*` 必须声明在 `body` 上

**规则**：皮肤里任何声明 `--dsw-*` 自定义属性的规则，其选择器必须落在 `body` 上（形如 `html[data-live-skin] body { … }` 或 `html[data-live-skin] body[data-ds-dark-theme] { … }`）。

**原因**：官方调色板声明在 `body`（`body{--dsw-alias-…}`）。皮肤的 token 若落在 `html` 上——**哪怕选择器特异性更高**——使用 token 的元素仍会从更近的祖先 `body` 继承到官方值。特异性只在**同一元素**上比较，这是最容易推错的一步。

**症状**：只有不走 token 的规则（例如直接写在 `body::after` 上的气泡）还看得见，其余全部退回官方外观。表现为「有气泡但没壁纸」。

**检查**：测试台 `[5] 皮肤 linter` → 「声明 `--dsw-*` 的规则必须落在 body 上」。

---

### C2 · 所有规则限定在 `html[data-live-skin]` 之下

**规则**：皮肤样式表的每个选择器都必须以 `html[data-live-skin]` 开头（`@keyframes` 的内部帧除外）。

**原因**：停用皮肤时样式表会被移除，但切换过程中存在窗口期；更重要的是，未限定的选择器会在皮肤被替换后留下残影，且让「停用」不再是干净操作。

**检查**：`[5b]` → 「C2 · 每个选择器都限定在 html[data-live-skin] 之下」。

---

### C3 · 变量必须有出处，参数不能是死旋钮

**规则**：
- CSS 里引用的每个 `var(--ls-*)`，必须是某个参数的 `cssVar`、某个 enum 选项派生的 `<cssVar>-dark`、或 CSS 自己声明的中间量；
- 反过来，声明的每个参数都必须在 CSS 里至少被引用一次。

**原因**：前者防拼写错误造成的静默失效；后者防「滑杆拉不动」——用户在面板里拉了半天，以为是插件坏了。

**检查**：测试台 `[5]` → 两条对应断言。

---

### C4 · 对比度底线

**规则**（针对每个 variant 的**两套**配色分别核验）：

| 组合 | 最低要求 |
| --- | --- |
| 正文文字 / 其所在面板底色 | 7:1 |
| 次要文字 / 面板底色 | 4.5:1 |
| 交互控件的描边 / 相邻底色 | 3:1 |
| 状态色（成功 / 警告 / 错误）/ 面板底色 | 4.5:1 |
| 填充按钮上的文字 / 填充色 | 4.5:1 |

**原因**：朋克美学天然偏爱低对比（蒸汽朋克的棕黄、柴油朋克的冷灰、赛博朋克的黑紫）。**氛围可以靠材质与光效表达，不能靠牺牲可读性。**

**落地手段**：底色可以暗、可以脏，但文字层必须显式抬亮；必要时给文字加一层极淡的描边或投影（`text-shadow: 0 1px 0 rgba(...)`），这是既往皮肤里已经验证有效的补偿手段。

**检查**：`[5b]` → 「C4 · 能静态解出的前景/底色对，对比度必须达标」。

---

### C5 · 动效只用合成属性，且必须可关

**规则**：
- 只动 `transform` / `opacity`。**禁止**动 `background-position`、`width`、`top`、`filter` 等触发重绘或重排的属性；
- 任何无限循环动效必须由某个 `boolean` 参数控制，且关掉后不留 GPU 合成层；
- `will-change` 只允许出现在**持续动画中**的元素上，不得停在静止的全屏层。

**原因**：官方皮肤性能规范明确点名「动画 `background-position` 会逐帧栅格化而非合成」。全屏逐帧重绘会直接出现在长任务火焰图里，用户感受到的是「这个插件一装就卡」。

**检查**：`[5b]` → 「C5 · @keyframes 只动 transform 与 opacity」。

---

### C6 · `backdrop-filter` 只用于小面积浮层

**规则**：只允许施加在**浮在内容之上**的表面：输入卡、会话头、对话框、菜单、Tooltip。**禁止**用于侧栏、整页底、大列表容器。

**原因**：实时模糊开销与覆盖面积成正比。而且——一个容易被忽略的事实——**背景若是平滑渐变，模糊在视觉上几乎不可见**。为看不见的效果付全屏 GPU 代价没有意义。

**检查**：`[5b]` → 「C6 · backdrop-filter 只出现在允许的浮层表面」。

---

### C7 · 只依赖稳定锚点

**规则**：装饰性选择器只允许使用：

- 语义属性：`[data-dsh-surface="…"]`、`[data-dsh-part="…"]`；
- 产品自身的稳定 state 属性：`body[data-ds-dark-theme]`；
- 皮肤自己的命名空间：`html[data-live-skin]`、`body::before/::after`。

**禁止**：`[class*=…]`、`[class^=…]` 这类基于 CSS-Module 哈希类名的匹配（官方一次重建就全废），以及任何形如 `.pI_x6G_frame` 的具体哈希类名。

**检查**：`[5b]` → 「C7 · 不使用哈希类名与 [class*=] 匹配」。

---

### C8 · 零外部资产

**规则**：不使用位图、字体文件、远程 URL、`@import`。所有纹理、图案、光效用 CSS 渐变与 `color-mix()` 表达。

**原因**：皮肤是资产目录，多一个文件就多一处路径逃逸与缓存失效面；纯 CSS 也保证皮肤在任何分辨率下都不糊。

**检查**：`[5b]` → 「C8 · 零外部资产」。

---

### C9 的来源

C9（不得注入可见文本）不是一条通用洁癖，它是赛博朋克卷「不把整个语系降格为异域贴纸」那条雷区规避的**可执行形式**。伪元素一旦能写文字，就一定会有人往界面里塞招牌——而招牌文字正是东方主义批评的靶心。

它对全部家族生效：67 支皮肤当前的非空 `content` 计数为 0。

---

### C10 · 皮肤不得重复声明参数自己的 cssVar

**规则**：皮肤 CSS 里不得出现 `--ls-<某参数的 key>: …` 这样的声明。

**原因**：运行时把参数值写成 `html` 上的**内联**自定义属性。皮肤若在 `body` 上再声明同名变量，按层叠规则，`body` 上的声明对 `body` 及其所有后代**永远获胜**——`html` 上的内联值只影响 `html` 自身。结果是滑杆能动、面板也显示新值，但界面毫无变化。这是 `[5]`「没有死旋钮」（检查每个参数是否被 CSS 引用）**抓不到**的一类静默失效：变量确实被引用了，只是引用到了一份皮肤自己写的副本。

**检查**：`[5b]` → 「C10」。

**实际收获**：这条检查一上线就查出**三个家族**里同一个 bug 的三个实例——
`AtompunkFamily` 与 `CassetteFuturismFamily` 各有一处**死变量**（声明了却没有任何引用，同时是 C3 违规），删掉即可；
`DieselpunkFamily` 的 `--ls-chrome` 与 `SolarpunkFamily` 的 `--ls-glass` 则**被下游引用**，改名才对。

这两条路走错的方向不同，但都会留下伤——于是有了 C11。

---

### C11 · 引用 number 参数时，兜底值必须与运行时写入的值同型

**规则**：对 `type: "number"` 的参数，每一处 `var(--ls-<key>, <兜底>)` 的兜底值必须匹配运行时的序列化形状 `<数字><unit>`（`unit` 未声明时即为空），且该引用必须落在能接受这种值的位置上。

**原因**：C10 只发现「变量名撞车」，但**修复方式本身会造出 C10 看不见的新伤**。修 `DieselpunkFamily` 时如果只是删掉 `--ls-chrome: #c8ccd0;` 而不管下游，`color-mix(in srgb, var(--ls-chrome) 46%, transparent)` 拿到的就是参数里的数字 `50`，整条声明在计算值阶段失效——滑杆依然是死的，而 C10 已经通过了。

契约的真正落点是**类型**：运行时写进 `number` 参数的一定是 `48` 或 `48px`。作者写下的兜底值就是他对「这个变量是什么」的声明，两者必须同型。

**检查**：`[5b]` → 「C11」。

**证伪记录**：注入两种违规各一次，均被抓住——`color-mix()` 消费 `--ls-chrome`；`var(--ls-blur, #ffffff)`（尺寸参数配颜色兜底）。

---

### C12 · 两档约定：谁在哪个模式生效，必须写清楚

**规则**（三条，缺一条就出「亮底浅字」）：

1. **默认块按它真正的归属限定档位。**
   - 「亮色默认 + 暗色覆盖」的家族，默认块写在 `html[data-live-skin] body:not([data-ds-dark-theme])` 上；
   - 「暗色默认 + 亮色微调」的家族，默认块保持 `html[data-live-skin] body`，把亮色微调放进 `body:not([data-ds-dark-theme])`。
2. **强制单一观感的变体**（如 `Cleanroom` 永远白、`DarkAero`/`Overgrown` 永远暗）必须把两个档的
   选择器**成对**列出：`body:not([data-ds-dark-theme]), body[data-ds-dark-theme]`。
   只写 `body` 会在亮色档输给大类的浅色块（(0,1,2) 输给 (0,2,2)）；只写 `[data-ds-dark-theme]`
   会在亮色档整块不生效，拿到大类默认块里的深色值。
3. **两档都要重画 `body` 底色。** `background-color` 与壁纸不在 token 体系里，不会被上面两条覆盖到。
   默认块是亮色的家族，暗色档要重画暗底；强制单一观感的变体，要重画自己的底色。
4. 参数派生的中间量（`--ls-*`）留在**两档共用**的规则里，只把 `--dsw-*` 调色板拆到分档规则里。

**为什么必须写清楚**：皮肤样式表由运行时**后插**进 head，所以谁生效由特异性决定，而不是文档顺序：

| 规则 | 选择器 | 特异性 |
| --- | --- | --- |
| 皮肤浅色块 | `html[data-live-skin] body` | (0,1,2) |
| 官方暗色块 | `body[data-ds-dark-theme]` | (0,1,1) |
| 皮肤暗色块 | `html[data-live-skin] body[data-ds-dark-theme]` | (0,2,2) |

中间那一行是这次故障的根：**皮肤在浅色块里声明、却没在暗色块里重写的 token，在暗色模式下拿到的是浅色值**
—— 它压过了官方暗色值。表现就是暗色档里输入框、代码块、列表选项、高亮还是亮的，配浅色文字整片看不见。

**检查**：`[5b]` → 「C4」，以及 `@body` 探针（正文压在实际页面底色上 —— 只看 `--dsw-alias-bg-base`
会漏掉「token 是暗的、但皮肤没给 body 画暗底」这一类，它的实际对比度是 1.04:1）。

---

### C13 · 强调色不能直接当正文链接

**规则**：`--dsw-alias-link` 必须是强调色的**正文安全版本** —— 相对强调色向页面反方向混合：

```css
/* 亮底：压深 */  --dsw-alias-link: color-mix(in srgb, var(--ls-accent, …) 42%, #0b1116);
/* 暗底：提亮 */  --dsw-alias-link: color-mix(in srgb, var(--ls-accent, …) 44%, #ffffff);
```

**原因**：强调色是为**填充与描边**挑的，不是为文字挑的。直接当链接用，橘色在米白页上只有 3.1:1，
亮绿在强制亮色的变体（`Cleanroom`）上只有 1.3:1 —— 链接是正文，得 ≥4.5:1。

**注意极性跟着**页面**走，不是跟着「模式」走**：暗色默认的家族（Steampunk / Dieselpunk / Biopunk /
Cyberpunk）两个档的页面都是暗的，链接两档都要提亮；强制单一观感的变体（`Cleanroom` 永远白、
`DarkAero` 永远暗）同理要写自己的链接。

**检查**：`[5b]` → 「C4」里的 `--dsw-alias-link on @body` 与 `on --dsw-specific-bubble` 两条探针。

## 四、验收流程

1. `node ../test/run.mjs` — 63 项断言全绿（含 `[5]` linter 与 `[11]` 线上新鲜度）。
2. 新增皮肤后，`[5]` 段会自动把它纳入检查（linter 遍历目录册里全部 variant）。
3. `[11]` 段确认线上 bundle 与磁盘一致 —— 皮肤是每次请求现读的，改完**刷新页面**即可，不需要重启。
4. 人工核验：设置面板里逐个切换 variant，检查面板自身在该皮肤下的可读性（**皮肤会改面板的配色，面板可能被自己的皮肤弄瞎**）。

## 五、已知的取舍

- **历史诚实 vs 氛围**：柴油朋克的「酷法西斯」、赛博朋克的东方主义、原子朋克的核灾难受害者缺位，都是真实雷区。本文档的立场见各分支规格的「雷区」小节：**可以借用视觉，必须与价值观保持距离**——具体做法是不使用可识别的敏感符号，并在皮肤描述里写明历史坐标。
- **忠实 vs 可用**：低对比是氛围的一部分。本文档选择「底色严守氛围、文字层强制达标」，代价是部分皮肤会比参考图「干净一点」。这是有意的。

## 六、自动检查（已实现）

C2、C4–C11 已经进测试台，对目录册里**每一个 variant** 逐一执行（C4–C11 在 `[5b] CSS 审计` 段）。验收台现有 **60 项断言**。

| 编号 | 断言 |
| --- | --- |
| C1 | 声明 `--dsw-*` 的规则必须落在 `body` 上（否则被官方调色板盖住） |
| C2 | 每个选择器都限定在 `html[data-live-skin]` 之下（遍历全部 variant） |
| C3 | 没有死旋钮：每个参数都真的被 CSS 用到；每个 `--ls-*` 都有出处 |
| C4 | 前景/底色**消费对**的对比度必须达标；按真实层叠（官方回落 + 特异性 + 各分支）解算，支持半透明与渐变，并有 `@body` 这条页面级探针 |
| C12 | 两档约定（见上）：限定块、成对选择器、重画 body 底色 |
| C13 | 链接必须是强调色的正文安全版本（≥4.5:1，含 `@body` 与气泡两处） |
| C5 | `@keyframes` 只动 `transform` 与 `opacity` |
| C6 | `backdrop-filter` 只出现在允许的浮层表面 |
| C7 | 不使用哈希类名与 `[class*=]` 匹配 |
| C8 | 零外部资产：不出现 `url()` 与 `@import` |
| C9 | 皮肤不得注入可见文本（`content` 只允许空串） |
| C10 | 皮肤不得重复声明参数自己的 cssVar（会压住运行时写在 html 上的内联值） |
| C11 | 引用 number 参数时，兜底值必须与运行时写入的值同型 |

### C4 的实现边界（重要）

只解算**能静态求值**的颜色：字面量、`var()` 指向字面量、以及 `color-mix(in srgb, …)`。`calc()` 与其它函数暂不解算，解不出就跳过。

为了不让它退化成空转，加了一条硬要求：**每个 variant 的「填充按钮上的文字」这一对必须能解算**，否则直接判失败。这条断言保证了解析器与皮肤写法不会悄悄脱节。

同时它还要求所有已解算的对全部达标。

### C4 上线当天的实际收获

写完之后第一次跑，它立刻报出**既有 `FrutigerAeroFamily` 的两个真实缺陷**：

```
AeroGlass:           白字 on #1f8fd6 = 3.52:1  < 4.5:1
FrutigerAero:        白字 on #0f7fc4 = 4.33:1  < 4.5:1
FrutigerAero (暗):   深字 on #0f7fc4 = 3.84:1  < 4.5:1
```

根因是**把品牌强调色直接当成了填充按钮的底色**。强调色用于描边与链接时浅色无妨，但填充按钮上要放文字，底色的相对亮度必须 ≤ 0.183（白字 4.5:1）。

修法：填充按钮的底色改为同一色相**压深**后的合成色（`color-mix(in srgb, var(--ls-accent) 80%, #00121c)`），强调色本身仍用于描边与链接。这一改动同时修好了「应用按钮 hover 变白」那个 bug 的同源问题。

### 检查自身的盲区（已修）

C2 最初只检查**一份** CSS blob（一个特定 variant 的 HTTP 响应），而且用「按行过滤」判断选择器，处理不了关键帧里的 `100% {` 这类节点行。它一直显示绿，只是因为被检查的那一份恰好用的是 `from`/`to`。

已重写为：遍历全部 variant，并用括号深度扫描把 `@keyframes` 整块剔掉再判断选择器。改完之后原子朋克家族（含 `0%, 100% {` 形式的关键帧）才真正进入这条检查的覆盖范围。

### C1 的同类盲区（已修）

C1 最初把**整条选择器字符串**拿去判断是否含 `body`。于是这种写法会被放过：

```css
html[data-live-skin],                          /* ← 这一段是漏的：token 落在 html 上 */
html[data-live-skin] body[data-ds-dark-theme] {
  --dsw-alias-bg-base: …;
}
```

整串里含有 `body`，正则就通过；但第一段把 token 写在了 `html` 上，会被官方 `body` 调色板盖住——正是 C1 要防的那个故障。

已改为**逐个拆分逗号列表**后分别判断。

### C4 解析器的同类盲区（已修）

C4 的取值解析器用「选择器字符串里有没有 `data-ds-dark-theme`」来判断一条规则是否只作用于暗色档。于是**浅色**规则 `body:not([data-ds-dark-theme])` 被误判成暗色，解析器在浅色模式下读的是基础（暗）块的值。

修法：先把 `:not(…)` 的内容剥掉再判断。

这个坑在 C1、C2、C4 上各出现了一次，**根因始终是同一个**：

> 检查的粒度不等于被测契约的粒度。
> C1/C2 的契约是「每个选择器」，检查却是「整条规则」；
> C4 的契约是「选择器实际匹配的元素」，检查却是「字符串里出现过什么」。

### C11 的同类盲区（已修）

C11 用一个 `enclosingFunction()` 回溯「这个变量最近的包裹函数是谁」。第一版取的是**最近的标识符**，遇到分组括号就返回空：

```css
--ls-cool-a: calc((100 - var(--ls-warmth, 50)) * .0032);
                            /* ↑ 往回第一个 ( 前面是 ( ，不是标识符 */
```

于是七处**完全合法**的写法被报成 `未知函数`。这和 C1/C2/C4 是同一个坑的第四次现身：契约是「最近的包裹**函数**」，检查却是「最近的**标识符**」。已改为跳过分组括号继续往外找。

### C4 的第二代盲区（已修，第五次同一个根因）

第一代 C4 只查 5 对手写的探针，且**皮肤没声明就跳过**。这两件事合起来让它对「亮底浅字」完全失明：
皮肤没写某个 token 不等于没问题，真相是官方值生效 —— 而且可能正好撞上皮肤自己挑的另一个值。
重写后它一次报出 **312 条**违规。

重写过程中同一个根因又出现两次：

- `ruleMode()` / `specificity()` 把**逗号列表整体**当成一个选择器。于是这种「两档都声明」的写法：

  ```css
  html[data-live-skin] body:not([data-ds-dark-theme]),
  html[data-live-skin] body[data-ds-dark-theme] { … }
  ```

  整串里含有 `data-ds-dark-theme`，被判成**暗色专属**，亮色档整块被跳过。契约是「列表里的每一个选择器」，
  检查拿的是整串 —— 与 C1/C2 完全同构。
- `bodyBackdrop()` 判断「这条规则是不是在画 body 的底色」时，被 `body::after`（一层贴图）和
  `body ::selection`（选中高亮）骗过：它们特异性更高，被当成了页面底色，于是一批半透明表面被算亮。

另外两处不是粒度问题，而是**模型问题**，同样是「检查的假设不等于现实」：

- 合成基准原本用「亮色档兜底白」。像柴油朋克那样把 `body` 画成不透明 `#3a3e40` 的家族，
  半透明表面实际是压在**它自己的底色**上，用白兜底会凭空算亮。
- 探针只比 `--dsw-alias-bg-base`（token），不看皮肤给 `body` 画的真实底色。原子朋克暗色档
  的 token 全是暗的、`body` 底色却还是米白 `#f3ebdd` —— 实际对比度 **1.04:1**，整页看不见，
  而第一版探针全绿。补 `@body` 探针才看见。

### 零件级 token 的暗色补齐（本轮新增）

「亮色默认 + 暗色覆盖」的家族往往只在暗色块里写主体面，剩下的**零件级 token**
（遮罩、滚动条、状态色、markdown 芯片、按钮变体、交互底色、阴影）在暗色档会沿用浅色值
或落回官方中性色。补齐的方式写在 `../plugin/scripts/gen-dark-parity.py` 里，
规则可复核、不含「猜」：

| 规则 | 说明 |
| --- | --- |
| 表面色 | 低饱和亮色按**亮度位置线性插值**到暗色梯子（最亮的抬起面 ↔ 最亮的暗面）；只换 RGB，alpha 表达式原样保留 |
| 强调色 | 原样保留（强调色与模式无关） |
| 反相描边 | 保留白色 |
| 墨色 | → 暗档正文色 |
| 状态色 | 取同色相的亮档版本 |
| **语义** | **由 token 决定，不由颜色决定** —— 见下 |

最后一条是踩出来的：同一个 RGB 在不同 token 里含义相反。

- Solarpunk 的 `#26301f` 既是 `label-primary` 的**墨色**（要翻成亮色），又是 `bg-mask-1` 的
  **深色蒙层**（要保持深色）。只按颜色匹配会把蒙层翻成亮色。
- `label-primary-foreground`（压在强调色按钮上的白字）和按钮填充的混色基 `#100c08`
  （近黑）都是**两档同值**的；按「亮面→暗面」翻转会把白字翻成暗绿、把深底翻成浅底 ——
  按钮立刻失去对比度。

**排查过程中的两次静默失败**（都是「粒度」问题的变体）：

1. 颜色字面量原本用正则提取，`rgba(248, 244, 236, calc(var(--ls-glass-alpha) + .26))` 这种
   **alpha 里套两层括号**的写法匹配不上，于是那条 token 被**静默跳过**、连「未映射」都不报。
   已改为括号平衡扫描。
2. 「表面」的判定阈值（饱和度 ≤0.12）把浅绿表面 `rgb(200,224,192)`（饱和度 0.143）漏掉了。
   已放宽到 0.16，并加了**产物自检**：生成结果里不允许再残留未处理的低饱和亮面。

### 面板样式纪律的两次失效（同一个根因的第六、第七次）

面板自己的样式表有两条纪律：改背景必钉文字色；填充态按钮要有自己的 hover 填充色。
用户的反馈「亮色时家族按钮选中态文字是黑的、和背景不区分」暴露了两处失效：

**① 契约是「任何状态组合」，检查却只看了 `:hover`。**

缺陷形态：`.ls-chip[data-on="true"]` 把文字钉成白（配它的强调色填充），
而 `.ls-chip[data-applied="true"]` **同特异性、源码在后**，只改文字色不跟着改底色 ——
亮色档下 `label-primary` 是深墨色，深底压深字。

检查已重写为精确判据：*同特异性 + 源码在后 + 只设 `color` 不设 `background` +
两条规则可同时生效（没有同一个属性被赋了不同值）* → 报错。

**② 检查自己会被一段注释悄悄弄哑。**

第一次给那条规则加注释之后，证伪**没有变红**。原因是解析用的正则把注释也算进了选择器，
分组键于是错开，两条规则永远配不到一起 —— 检查静默失效，却仍然显示绿色。
三条 `[7c]` 检查现已统一走 `panelRules()`，**先剥注释**再解析。

这条与「检查的粒度不等于被测契约的粒度」是同一族，但更隐蔽：前几次是**测得不够宽**，
这次是**自己被输入格式弄哑**。两次都是靠证伪（注入违规、确认它会红）才发现的。

### 教训（五次同一个根因）

一条「永远绿」的检查比没有检查更危险——它让人以为有覆盖。凡是新增检查，都要做一次**反证**：故意注入违规，确认它会红。

> **检查的粒度不等于被测契约的粒度。**
>
> | 检查 | 契约的粒度 | 第一版实现的粒度 |
> | --- | --- | --- |
> | C1 | 每个选择器 | 整条规则字符串 |
> | C2 | 每个 variant 的全部 CSS | 一份 CSS blob（且按行过滤） |
> | C4 | 选择器实际匹配的元素 | 字符串里出现过什么 |
> | C11 | 最近的包裹**函数** | 最近的**标识符** |
> | C4（第二代） | 选择器**列表里的每一个** | 整串字符串 |
> | C4 的页面底色 | 皮肤给 `body` 画的**实际底色** | `--dsw-alias-bg-base` 这个 token |
> | 面板样式纪律 | **任何**会改背景的状态组合 | 只看 `:hover` |
> | 面板样式纪律（解析） | 剥掉注释后的规则 | 带上注释文本的「选择器」 |
>
> C10 → C11 是这条教训的另一种形态：**修一个 bug 的手法本身会引入新 bug**。C10 只断言「不许同名」，但合法的修法有两条（删死变量 / 改名），选错就得到 C11 才管得住的那类伤。检查写完不等于契约闭环——还要问「按这条检查去修，会不会修出它看不见的伤」。

### 仍未覆盖

- **半透明底上的对比度**：面板底色普遍是 `rgba(…, calc(…))`，实际对比取决于它背后的壁纸。静态解算无法判定，目前跳过。
- **真实渲染验证**：自动检查只能证明「CSS 写对了」，不能证明「看上去对」。每加一个家族仍需人工在设置面板里逐个切换 variant 看一眼。
